# 版本、分支与发布策略

## 定位与决策

本规范仅适用于本仓库。版本、标签、里程碑和发行制品独立维护，不与其他项目绑定发版。

本项目是通用 Subversion 命令封装与结构化解析库。保持轻量、无第三方运行时依赖，不内置特定下游的业务流程、GUI 或服务端。支持原生能力不等于模拟或改写 SVN 行为。

- 保留 SVN 原生修订、peg、目标范围、权限、钩子和提交原子性；不猜测编码或修订，不自动扩大目标，不拆分一次原子提交。
- 新需求按通用性、兼容性、测试证据和持续维护成本评估，不因提交者身份不同而改变标准。合理需求可以延期，不等于承诺实现日期。
- 原生客户端缺陷先通过隔离复现和官方依据确认；文档说明或环境绕行不等于上游问题已修复。
- 维护者负责范围、合并和发布决定，贡献者提供可核验的变更。争议在 issue 记录依据和备选方案；影响公共契约的决定必须进入文档和变更日志。
- 不承诺几年内零升级、所有 SVN 宿主兼容或固定响应时限。稳定性以公开契约、回归测试和可追溯发布保证。

## 版本与兼容性

版本唯一来源是 `pyproject.toml` 的 `[project].version`。正常版本使用 `X.Y.Z`，预发布使用 `X.Y.Zrc1` 等 [PEP 440 格式](https://packaging.python.org/en/latest/specifications/version-specifiers/)；包版本不带 `v`。

| 阶段 | 版本变化 | 本项目规则 |
| --- | --- | --- |
| 0.x | PATCH | 兼容修复、打包修正，以及不改变已有调用/默认行为的小型可选增强 |
| 0.x | MINOR | 较大能力新增、弃用公告；不可兼容变更只能在此边界经专项评审引入 |
| 1.0 及以后 | PATCH | 向后兼容的缺陷、安全或打包修复 |
| 1.0 及以后 | MINOR | 向后兼容的新能力和弃用公告 |
| 1.0 及以后 | MAJOR | 完成弃用流程后仍确需引入的不可兼容变化 |

0.x 采用上表的项目兼容约定，不把 SemVer 的开发阶段解释为可以随意破坏行为。1.0 起采用 [SemVer](https://semver.org/) 的递增原则，Python 预发布拼写仍遵循 PEP 440。任何版本都不得违反 SVN 原生规则。

公共契约包括：
- 公共导入、方法签名、默认值、模型字段、返回值和异常契约。
- Path 与字符串的目标语义、revision/peg、状态范围及原生 bytes 输出。
- 非交互执行、可选超时、进程树清理、输出预算和原子下载。

### 版本更新时机

- 普通提交和 PR 不修改版本号；行为变化累计写入 CHANGELOG“未发布”。发布准备 PR 根据本次全部变更统一选择版本，并同步元数据、README 和变更日志。
- main 的版本号可以暂时保留上次正式版本，不代表当前源码等同该发行包。报告源码问题须记录完整提交 SHA 和未提交修改情况。
- 同版本的本地构建仅用于验证，不作为新的正式包分发。需要对外提供候选包时使用尚未发布的 `X.Y.ZrcN`；候选包更新必须递增 `N`，正式发布再定版。
- 不按提交次数或 issue 数量递增版本，不因纯规范文档合并而创建发布标签或上传 PyPI。

### 兼容性处理

- 纯贡献文档、测试或 CI 变更可以只合并，不为此强制发 PyPI 包；发行制品发生变化时必须使用新版本。
- 不在补丁版中删除参数、改变默认目标/超时、提高 Python 最低版本或移除受支持平台。缺陷修复恢复既有文档契约时，也要披露可观察变化。
- 普通弃用至少经过一个已发布 MINOR 版本，并留出六个月迁移期，再在允许破坏兼容的版本边界移除；记录首次弃用版本、替代方案和最早移除版本/日期。
- 紧急安全修复无法保留不安全行为时，维护者记录例外原因、影响及迁移方式，不隐藏行为改变。
- 发布 `1.0.0` 前需要公共契约清单、支持矩阵、核心真实 SVN 回归、候选版和下游验收记录。不能仅因希望“长期稳定”而直接改成 1.0。
- 不使用 `.postN` 发布代码缺陷修复；预发布不是稳定版。正式版需重新定版检查，不能只移动 rc 标签。

## 维护范围

默认只维护最新 MINOR 系列的最新正式补丁版。旧版问题仍可报告；维护者确认影响后决定升级修复或显式回补，不静默承诺多个长期维护系列。

旧系列只有在本文登记负责人、截止日期、支持平台及验证要求后，才建立 `maintenance/X.Y` 分支；目前没有额外 LTS 系列。安全问题的报告和处理见 [安全政策](../SECURITY.md)。

Python 最低版本以项目元数据为准，实际验证平台以 CI 和发布记录为准。兼容已停止上游维护的 Python 不等于为该运行时提供安全支持。平台/认证未实测时必须标明，不能把测试跳过记为通过。

## 分支与合并

| 分支 | 来源与目标 | 用途 |
| --- | --- | --- |
| `main` | PR 合并目标 | 保持可测试、可构建；不等于已发布 |
| `fix/<issue>-<slug>`、`feat/<issue>-<slug>` | 从 main 建立，合回 main | 单一修复或已接受需求 |
| `docs/<slug>`、`chore/<slug>`、`refactor/<slug>` | 从 main 建立，合回 main | 文档、工具链或等价重构 |
| `release/<version>` | 从 main 建立，合回 main | 可选的版本号、日志和发布准备 |
| `hotfix/<issue>-<slug>` | 通常从 main 建立 | 紧急修复，检查门槛不降低 |
| `maintenance/X.Y` | 从该系列已发布标签建立 | 仅用于明确承诺的旧系列维护 |

不维护长期 `develop`，不为每次发版建立永久 release 分支。分支名使用小写 ASCII 和短横线；无 issue 的纯文档变更可省略编号。版本和提交信息记录在 issue/PR 中，不塞进分支名。

外部贡献从 fork 提交 PR；维护者也使用 PR 留下范围、证据及评审记录。通常使用 squash merge，标题采用 `fix:`、`feat:`、`docs:`、`test:`、`refactor:`、`chore:` 或 `release:` 加简短摘要，中文或英文均可。保留作者和必要的共同作者归属，不要求强制签署未配置的 CLA。

至少由一名有权限的维护者审查外部贡献。维护者自提 PR 优先由另一人评审；单人维护时明确记录自审及测试结果，不声称独立审查。合并后删除已完成的短期分支；不得改写 main 或已发布历史。

若 main 已包含不能回补的内容，hotfix 从受维护系列标签建立，经维护分支发布，再把等价修复通过独立 PR 同步回 main。保留原修复来源，避免直接把维护分支整体合入而混入版本回退。

## Issue 基线

Issue 属于仓库，可以报告任意已发布版本或维护分支的问题，不默认指向最新 main。发现版本与修复起点分开记录：

| 记录 | 内容 | 维护位置 |
| --- | --- | --- |
| 发现基线 | 正式包的精确版本和安装来源；源码的分支、完整提交 SHA、未提交修改情况 | Issue 原始报告 |
| 复现条件 | Python、操作系统、SVN 客户端、最小复现及相关配置 | Issue 原始报告 |
| 修复起点 | 分支创建时的基准分支及完整 SHA、拟合并分支 | 修复 PR |
| 验证记录 | 每次复测的精确版本/SHA、环境、命令和结果 | Issue / PR 后续回复 |
| 发布归属 | 实际包含修复的标签和 PyPI 版本 | 发布后回复及 CHANGELOG |

- PyPI 用户不必查 Git SHA；源码用户不能仅填写版本字符串，因为多个提交可能保留相同包版本。自建 wheel 可补文件 SHA256。
- 使用实际运行的环境采集版本，并核对模块导入路径。Git SHA 只标识源码提交；未提交修改需单独说明，必要时附最小脱敏 diff。
- 分支和包版本不能唯一描述修改后的工作区。未提交代码的复现结果不得归为该 SHA 的干净源码结果；标签应同时记录其指向的提交，源码引用使用 [固定提交链接](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)。
- 只记录已验证的受影响版本及最后正常版本；未知项写“未知”，不推断整个版本区间。无需为了报告问题升级生产环境。
- 保留原始报告的发现基线，复测追加记录。main 不再复现时，先对照原版本及相同用例，再说明是已定位修复、环境差异还是原因未确认；不能据此直接判定原报告无效。
- 修复分支通常从当前 main 建立，不必从出错提交开始；旧系列回补按维护分支规则另开 PR。同一问题可关联多个 PR，里程碑仅表示计划修复版本，不表示受影响版本。
- PR 后续 rebase 或更新基线时追加新基线记录，不覆盖最初起点。分支名只用于识别任务，不作为历史版本证据。

采集信息的命令和填写示例见 [issue 例文](issue-examples.md)。无法安全获取的信息可注明原因，由维护者协助核实。

## Issue 状态与关闭

[提交规范](../CONTRIBUTING.md)适用于所有提交者。类型使用 `bug`、`enhancement`、`documentation`；以下状态由维护者在回复或可选标签中记录，不依赖机器人自动流转。

| 状态 | 必须说明 |
| --- | --- |
| 待分诊 | 范围、影响和现有证据 |
| 待信息 | 缺少哪些最小信息；不得索取凭据或生产资产 |
| 已接受 / 延期 | 接受范围、限制和阻塞原因；未排期不承诺版本 |
| 处理中 | 关联 PR；仅本地实现须明确“未合并” |
| 已合并未发布 | 合并提交、验证结果和计划版本（如有） |
| 已发布待验收 | tag、PyPI 版本、已验证环境及剩余验收项 |
| 已关闭 | 完成证据，或重复/不适用/证据不足的具体理由 |

代码缺陷默认等正式包发布并核验后关闭；需要特定宿主验收的项目继续保持开放。纯文档修正可以在文档合并后关闭，但不能连带关闭尚未修复的原生限制。

代码 PR 用 `Refs #N` 关联，避免 `Fixes/Closes/Resolves #N` 在合并时提前关闭未发布缺陷。重复项链接原 issue；无法复现时记录尝试环境并请求信息，不直接判定用户错误。长期待信息项可在提醒后人工关闭，并允许补充证据后重开；不启用自动 stale 关闭。

优先级按数据损坏、安全/错误写入、核心流程阻断、一般缺陷、兼容增强和文档排序，不按提交者身份或留言次数排序。里程碑用计划版本号，加入前确认发布范围；延期或移出时给出原因。

## 发布与标签

发布由有权限的维护者显式执行。PR 合并、推送标签、创建 GitHub Release、上传 PyPI 是不同动作；当前 CI 不自动上传 PyPI。

1. 分诊并确定本次范围，排除无验收证据的能力；更新版本、中文 CHANGELOG、README 及相关参考文档。
2. 发布准备 PR 合入 main（或登记的维护分支）后，在干净工作区核对完整提交 SHA。确认该提交而非旧 PR 提交的 CI 通过；有新提交就重新确认。
3. 运行 [发布指南](releasing.md)中的保护脚本，完成全量检查、真实 SVN 核心测试、sdist/wheel、归档白名单、Twine、隔离安装和导入验证。记录跳过项；核心 SVN 测试不得因缺少工具而跳过验收。
4. 查询远端 tags 和 PyPI，确认新版本未使用。创建 annotated `v<version>`，只推送该标签，核对远端 tag 对象和 peeled commit 与本地一致。
5. 显式调用保护脚本上传正式 PyPI，不使用 `--allow-dirty`、`--skip-checks` 或绕过脚本的直接上传。
6. 从正式 PyPI 核对每个文件的 SHA256，在新环境无缓存安装精确版本并运行 `pip check`、公共导入及核心冒烟。
7. 为已有同一标签创建 GitHub Release，列出中文变更、兼容性、限制、CI/测试环境和制品 SHA256；上传成功之前只能是 draft，rc 标记为 prerelease。
8. 回填 issues 的提交、标签、包版本和验收状态；满足关闭条件后再关闭。

标签统一为 `vX.Y.Z` 或 `vX.Y.ZrcN`，版本文字必须与元数据相同。不新建无前缀标签；脚本接受无前缀只是历史兼容，不是推荐命名。签名标签可选，不能以未配置的签名要求阻断一般贡献。

推送过的发布标签不得移动、覆盖或删除后重建，即使 PyPI 尚未上传。修订内容使用新版本；未发布的旧标签应注明发布取消。GitHub Release 页面内容可补充勘误，但不可改变其标签指向。

正式上传脚本会重新构建，以该次上传文件和输出哈希为准；预检产物不自动等于最终产物。每次上传使用独立版本目录（`--dist-dir`）保留证据。wheel/sdist 不包含贡献指南、模板、CI、测试、开发环境配置或其他包实现。

## 发布失败与回退

- 上传失败或中断：先检查 PyPI 已接受的文件及哈希，保留本地原件，不盲目重建重传，不用 `--skip-existing` 掩盖差异。当前脚本没有续传模式；由维护者先确认部分发布状态，无法安全完成时用新版本修复。
- 错误发布：标注影响，必要时 [yank 整个版本](https://docs.pypi.org/project-management/yanking/)并填写原因，然后发布新修复版本。yank 不会卸载现有安装，也不能阻止所有精确锁定安装。
- 不删除旧版本来“复用”版本号，不强推旧 tag；回退代码使用新的 PR 和版本，用户回退安装须先评估数据及兼容性。
- SVN 写操作超时可能已经提交；先核验远端状态，不能自动重试或撤销生产提交。

## GitHub 管理员配置

以下是需要在 GitHub 启用的设置，不会因本文件存在而自动生效。实际可用性取决于仓库可见性、套餐及权限，配置后应使用测试 PR 核对规则。

- 为 main 和已登记维护分支要求 PR、对话解决、最新目标基线检查通过，禁止强推和删除；默认 squash merge，开启合并后删除短期分支。
- 必需检查选择当前 CI 的四个实际 job：`ubuntu-latest / Python 3.9`、`ubuntu-latest / Python 3.12`、`ubuntu-latest / Python 3.14`、`windows-latest / Python 3.12`。以后修改矩阵时同步更新要求，不能要求不存在的 job。
- 多维护者时要求至少一次批准并使过期批准失效；单维护者自提 PR 使用公开记录的自审例外。不要把 CI 或秘密检查一起作为日常 bypass。
- 对 `v*` 建立 tag ruleset：创建权限仅给发布维护者；更新和删除保护应单独配置，避免创建标签的 bypass 同时放开覆盖已发布标签。紧急管理权限只作审计留痕后的恢复。
- 启用私密漏洞报告（如仓库支持）、2FA、可用的秘密扫描/推送保护；权限按贡献审查和发布职责分别授予。
- fork PR 仅做不含生产凭据的检查。审查首次贡献者工作流后才允许运行；不得用 `pull_request_target` 检出并执行不受信任分支。未来发布工作流采用受保护环境和人工审批，配置 Trusted Publishing 后另行验证。
- 增加维护者前在 PR 记录职责和授权范围；撤销不再需要的仓库、PyPI 或自动化权限，不共享个人 token。

规则能力参考 [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)。发布脚本保护的是工作区、质量检查和标签一致性，不替代 PR 审查、分支保护或人工发布授权。
